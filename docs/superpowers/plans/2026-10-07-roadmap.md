# Terminal Sigma 2.0 Roadmap

This roadmap splits the request into 5 plans, each of which ships working, tested software on its own. It records the research behind each decision and the contracts the plans share, so a plan's executor can rely on names the other plans define. Every plan follows [`CLAUDE.md`](../../../CLAUDE.md) and the path rules in [`.claude/rules/`](../../../.claude/rules/).

## The Plans

The plans run in order: each one starts from the code the one before it leaves behind:

| Order | Plan                                                              | Delivers                                                                                                                         | Release |
| ----- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ------- |
| 1     | [A: Environment Settings](./2026-10-07-a-environment-settings.md) | An **Environment** menu item that shows and edits every environment variable, saved to a private `config.json`                   | `feat`  |
| 2     | [B: Quote Change Notice](./2026-10-07-b-quote-change-notice.md)   | A `✦ New` badge and a typing effect whenever the everyday quote changes                                                          | `feat`  |

| 4     | [D: Living Character](./2026-10-07-d-living-character.md)         | A character whose body, face, hair, and mood follow every small profile change and log, plus time of day and seasons             | `feat`  |

Each plan is several commits on 1 branch, merged to `main` when its last task passes. Because every `feat` on `main` publishes, merge a plan only when it is whole.

## Hard Constraints

These come from the request and hold in every plan:

- **Offline First**: No cloud backup, sync, accounts, or real-time chat. The only network calls are the ones a user opts into with a key: API Ninjas quotes, an AI provider, and Langfuse. With no key set, the app never touches the network
- **One Codebase, 2 Builds**: The NPM CLI and the Electron app keep rendering the same `App`
- **Old Files Keep Loading**: Every new field is optional or defaults to `[]`, and each plan that touches the schema adds a test that loads a `progress.json` written by 1.6.0

## Decisions

### Stay on TypeScript and Ink

Rust (`ratatui` 0.30, `ratatui-image`, `tachyonfx`), Go (Bubble Tea v2), and OpenTUI 0.5 all hit the same terminal ceiling Ink does: 1 foreground and 1 background color per cell. Each would mean rewriting about 7,000 lines, shipping per-platform binaries through NPM, and giving up the shared `App` in the desktop build; OpenTUI also needs Node.js 26.4 or Bun, against this package's `>= 22`. Godot 4.7 has the best animation tooling but no terminal at all, so it would fork the product. Ink 7 already gives what the animation needs: `useAnimation({ interval, isActive })` with `time` and `delta` on 1 shared timer, `maxFps`, incremental rendering, and synchronized output.

Finer block characters do not help color art: sextants and octants raise resolution but force each cell down to 2 colors, and xterm.js's stable WebGL addon draws neither. The half-block `▀` stays the character's pixel. Image protocols (Kitty, Sixel, iTerm2) skip Terminal.app entirely, fight Ink's renderer, and are still alpha in xterm.js, so they are out.

Deferred, as separate work after Plan D: upgrading to Ink 8 (line-diff rendering, needs React 19.3), and a desktop-only `<canvas>` over the character panel, fed over IPC with the pixel grid `composeScene` already produces. The canvas is the only route to larger sprites, and it costs the CLI nothing, but it needs its own art pipeline.

### Paint the Character, Do Not Import It

The [LPC character generator](https://github.com/LiberatedPixelCup/Universal-LPC-Spritesheet-Character-Generator) has the right content, but its frames are 64×64 pixels, which would take 64 columns by 32 rows as half-blocks; pixel art does not survive shrinking to the 34×40 stage. Its code is GPL-3.0, and only some of its art is CC0 or attribution-only, so it would also force a `CREDITS` file and a dual license. LimeZu's packs forbid redistribution, and publishing to NPM is redistribution. Plan D therefore keeps painting the character procedurally, which already recolors with every theme, and makes every input continuous. If the desktop canvas ever happens, bundle only CC0, OGA-BY, or CC-BY art with a credits file.

### Log from 1 Command Line

The fastest food loggers win by cutting actions, not screens: MacroFactor needs 24 actions across its speed test against 33 for the runner-up, by remembering servings, suggesting the foods you eat at this hour, and stamping the current time. Copying yesterday was MyFitnessPal's most requested feature. Hevy and Strong prefill the last sets. Daylio logs a mood in 2 taps. A keyboard-only terminal does all of this best as 1 line with short ASCII prefixes, which also work through a Chinese or Korean input method:

```text
2 eggs, toast, coffee        → 3 meal items, matched in any language
450kcal 30p                  → a quick-add meal
w 500                        → 500 ml of water
wt 72.4                      → body weight
sl 23:30-7:10 q4             → sleep and its quality
m 4 e3 #work                 → mood, energy, and tags
wo bench 60x5x3              → strength: 60 kg, 5 reps, 3 sets
wo run 30m hard              → cardio
h read                       → a habit done; "h read s" skips today
st 8400                      → steps
n grateful for the sun       → a note
@y 21:00 …                   → any of the above, yesterday at 21:00
.                            → repeat the last entry
u                            → undo
```

The data that can ship inside an MIT package: USDA FNDDS (CC0, household portions for 5,432 foods), the Taiwan FDA food composition set (Open Government Data License 1.0, attribution), the Korea MFDS everyday foods (no restrictions), `yuhonas/free-exercise-db` (Unlicense), and MET values from the 2024 Adult Compendium of Physical Activities (free to use with a citation, values unchanged). Open Food Facts (ODbL share-alike), wger (CC-BY-SA), and ExerciseDB (AGPL) are out.

### Call AI Through the AI SDK, Behind a Fallback Chain

The [AI SDK](https://ai-sdk.dev/) 7.0 (`ai` 7.0.130, Node.js 22, zod `^4.1.8`) speaks to OpenAI, Anthropic, Google, and xAI through `@ai-sdk/openai`, `@ai-sdk/anthropic`, `@ai-sdk/google`, and `@ai-sdk/xai`, and to any OpenAI-compatible server through `@ai-sdk/openai-compatible`. That last one covers Ollama, LM Studio, OpenRouter, and [OmniRoute](https://github.com/diegosouzapw/OmniRoute) (MIT, `http://localhost:20128/v1`), so a user who already runs a gateway can point Terminal Sigma at it. Plan E loads every provider with `import()` only when an account uses it, so a user without AI pays no start-up cost.

The fallback is Terminal Sigma's own loop over an ordered list of accounts. The conversation is stored provider-neutral, so the next account simply receives the same messages. Langfuse JS 5 traces each request as 1 trace through `@langfuse/otel`'s `LangfuseSpanProcessor` and `@langfuse/vercel-ai-sdk`, registered with AI SDK 7's `registerTelemetry`, and only when both Langfuse keys are set.

> [!warning]
> OpenAI's terms forbid "circumvent[ing] any rate limits", and Google's API terms forbid bypassing protective measures. Plan E builds fallback across providers and across the user's own keys for resilience, the way LiteLLM and OpenRouter do. It deliberately has no round-robin or "spread load over many free accounts" mode, and the README tells users that rotating free accounts of 1 provider to dodge its limits can get them banned. A local model through Ollama is the free, unlimited fallback.

### Keep Settings Apart from the Journey

`progress.json` stays portable and secret-free. Environment variables and AI accounts live in `config.json`, mode 600, beside it; a saved `TERMINAL_SIGMA_HOME` moves only `progress.json`, so keys never ride along into a synced folder. AI conversations live in `coach.json`, so deleting them never touches the journey.

### The Schema

Plan C adds these to `progressSchema`, every array defaulting to `[]`. Amounts on a meal are totals for the entry, already multiplied by its servings, so every existing sum stays right:

| Field                   | Shape                                                                                              |
| ----------------------- | -------------------------------------------------------------------------------------------------- |
| `body`                  | `{ at, weight?: 30-300, waist?: 40-250, bodyFat?: 3-60 }`, at least 1 of the 3                     |
| `goals`                 | Optional `{ water?: 250-10000 ml, sleep?: 240-720 min, steps?: 1000-50000, focusSessions?: 1-16 }` |
| `habits`                | `{ at, name: string, amount?: > 0, skipped?: boolean }`                                            |
| `meals[].carbs`, `.fat` | Optional grams, `>= 0`                                                                             |
| `meals[].servings`      | Optional, `> 0`                                                                                    |
| `moods`                 | `{ at, score: 1-5, energy?: 1-5, stress?: 1-5, tags?: string[] }`                                  |
| `notes`                 | `{ at, text: 1-2000 characters }`                                                                  |
| `sleep`                 | `{ at: the wake time, minutes: 1-1440, quality?: 1-5 }`                                            |
| `steps`                 | `{ at, count: 1-100000 }`                                                                          |
| `water`                 | `{ at, milliliters: 1-5000 }`                                                                      |
| `workouts[].calories`   | Optional kcal from MET × kg × hours                                                                |
| `workouts[].distance`   | Optional km, `> 0`                                                                                 |
| `workouts[].sets`       | Optional `{ exercise: string, reps: >= 1, weight?: kg >= 0 }[]`                                    |

Plan D adds optional appearance fields to `profile`: `skinTone` (`1`-`5`), `hairStyle` (`short`, `long`, `bob`, `ponytail`, `bun`, `buzz`), `hairColor` (`black`, `brown`, `blonde`, `red`), `glasses` (boolean), and `facialHair` (`none`, `stubble`, `beard`). Plan E adds `plans: { at, title, days: { weekday: 0-6, activity, minutes, intensity, note? }[] }[]`, defaulting to `[]`.

### Logs and Experience

From Plan C, `logsOf` returns every entry with `kind`, `at`, `index` (its position in its own array, which edit and delete use, since 2 items of 1 line share a timestamp), `experience`, and `entry`. The kinds are `focus`, `meal`, `workout`, `water`, `sleep`, `body`, `mood`, `habit`, `steps`, `note`, and `event`. Experience stays derived, never stored; new kinds earn a little, capped per local day so logging can never be farmed:

| Kind    | Each        | Daily Cap |
| ------- | ----------- | --------- |
| `body`  | 5 XP        | 5 XP      |
| `habit` | 5 XP        | 25 XP     |
| `mood`  | 3 XP        | 6 XP      |
| `note`  | 3 XP        | 3 XP      |
| `sleep` | 10 XP       | 10 XP     |
| `steps` | 1 per 1,000 | 20 XP     |
| `water` | 1 XP        | 8 XP      |

`todayOf(progress, now)` gains `water` (ml), `sleepMinutes`, `steps`, `mood` (the latest score or `undefined`), `habitsDone`, and `caloriesBurned`. `targetsOf(profile, goals?)` gains `water`, `sleep`, `steps`, and `focusSessions`, with `goals` overriding each.

## Skills and Rules to Install

Install only after reading every file of the skill, since a skill becomes instructions for every later agent:

| Skill                                                                                           | License | Why                                                                                     |
| ----------------------------------------------------------------------------------------------- | ------- | --------------------------------------------------------------------------------------- |
| [`terminal-ui`](https://github.com/pproenca/dot-skills/tree/master/skills/.curated/terminal-ui) | MIT     | 42 rules for Ink: rendering, flicker, and input handling; read before Plans B, C, and D |

It lives at `skills/.curated/terminal-ui` in `pproenca/dot-skills`, last pushed on 2026-08-15. Copy it into the repository, read it, and commit it only if nothing in it contradicts [`CLAUDE.md`](../../../CLAUDE.md) or the path rules:

```shell
git clone --depth 1 https://github.com/pproenca/dot-skills.git "$TMPDIR/dot-skills"
cp -R "$TMPDIR/dot-skills/skills/.curated/terminal-ui" .claude/skills/terminal-ui
```

The `superpowers` skills already cover planning, test-driven development, and review. No credible skill exists for Ink pixel art, and Langfuse and the AI SDK have none worth installing; Plan E adds its own rule, `.claude/rules/ai.md`, instead.

## Out of Scope

- Barcode and photo logging, which need a camera
- Cloud backup, sync, or sharing
- Importing Apple Health or Google Fit exports, a good later addition because it stays offline
- Ink 8 and the desktop canvas, as described under the first decision
- Screen time, which no offline source can provide
